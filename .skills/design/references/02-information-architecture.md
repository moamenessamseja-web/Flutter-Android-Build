# Information Architecture

Start with the domain, not the cards. Identify entities, relationships, events, source values, derived values, states, and permissions. Keep source data separate from calculated/estimated values.

For each task record entry point, required information, steps, decision points, success, error/recovery, frequency, and importance.

Choose navigation by hierarchy and task frequency: bottom navigation for a few peer primary destinations; drawer for secondary/global management; tabs for peer views in one context; detail page for one entity's history; sheet/dialog for short contextual actions. Do not add navigation to fill empty space.

Each real-world entity needs stable identity. Do not merge separate records because they share a category. Define sorting, grouping, filtering, empty state, long-name behavior, and enough identifying information to distinguish similar records. Avoid nested independent scrolling areas.

For every home-screen item ask: needed immediately? helps choose next action? can move to details? redundant? Aggregates must state their period and basis; do not combine incomparable values.
