# Design Critique

Re-read the brief; inspect the actual screen/build; trace the primary task; evaluate seven competencies; record evidence, impact, and correction; separate preference from usability failure; re-check after changes.

Score each 1–5 as a review aid, not scientific measurement:

| Competency | 1 — Weak | 3 — Adequate | 5 — Strong |
|---|---|---|---|
| Visual Hierarchy | competing emphasis | readable, some conflicts | clear scan path |
| Information Architecture | tasks/entities confused | mostly understandable | mirrors tasks/domain |
| Visual Language | inconsistent/generic | coherent | distinctive and appropriate |
| Component Composition | excessive containers | reusable with clutter | purposeful, disciplined reuse |
| UX Design | missing feedback/recovery | main flow works | complete, resilient, accessible |
| Design to Development | fragile/drifts | maintainable | faithful, responsive, tokenized |
| Design Critique | no evidence/criteria | issues identified | evidence-led iteration |

Severity: **P0** core task impossible/data loss/critical accessibility; **P1** likely misunderstanding or serious friction; **P2** hierarchy, density, consistency, responsiveness; **P3** minor polish.

Finding format: [Severity] Element/state → Evidence → User impact → Correction → Acceptance check. Label evidence as screenshot, source, running app, CI, artifact, or owner-device review. Never call a concept implemented.
